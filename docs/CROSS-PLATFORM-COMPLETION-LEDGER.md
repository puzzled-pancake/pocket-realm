### Round 1 (bug-hunt r1)

#### 5.1 — medium (status: unconfirmed)

**What:** The mode-aware interface-loss liveness did NOT land as one implementation (contrary to the design's own decision 6, docs/DESKTOP-MULTIPLAYER-AND-TIMEFRAME-DESIGN.md lines 136-141: '§1 D1/D2 and §2 §10 must land as one implementation, not two'): the two platforms run two hand-rolled monitor loops whose watch input diverges — desktop reads the LIVE settings store, Android reads the spec-frozen runtime snapshot — so on desktop a mid-session Settings edit re-targets the watchdog of a live hosted session and can graceful-stop a healthy realm.

**Evidence:** Desktop: LanInterfaceLossMonitor.tickOnce (desktop/src/main/kotlin/com/pocketrealm/desktop/DesktopAppModel.kt:104-107) takes its tunnel input from the `advertised` seam wired to `tunnelAdvertisedForWatch()` (DesktopAppModel.kt:333), which reads the live settings store `_settings.value` (DesktopAppModel.kt:1101-1112) — and additionally escapes to the LAN leg when advertised == bind endpoint (`?.takeIf { it.value != snapshotValue.realmEndpoint.address }`, line 106). Android: the monitor leg keys off `InterfaceWatch.forSession(snapshot.advertisedAddress)` (android/app/src/main/java/com/pocketrealm/service/RealmService.kt:619) where snapshot.advertisedAddress is frozen from the launch spec at start (RuntimeModel.kt:47-53; DurableRuntimeSupervisor.kt:88) with no bind-equality escape. The desktop field feeding it is live-editable during hosting with no disabled-while-running gate (desktop/src/main/kotlin/com/pocketrealm/desktop/ui/SettingsScreen.kt:878-882 — onValueChange -> model.updateSettings unconditional). Concrete kill paths on desktop only: clear the advertise field mid-tunnel-session -> watch flips to the private-LAN leg, which fails on a remote-only host -> healthy tunnel session saved-and-stopped after the 10 s grace; or type an advertise value mid-LAN-session -> watch flips to a tunnel adapter that is not up -> same stop. On Android the same edit cannot affect the running session's watchdog. Reachability caveat: verified by code reading; no runtime repro executed (single host machine — same 'no two-machine join' limitation the design doc itself states). Phase sets and grace windows do match (both MONITORED_PHASES = WORLD_READY/RUNNING/PAUSED/CLIENT_FAILED; 10_000 ms grace: RealmService.kt:800, DesktopAppModel.kt:207).
