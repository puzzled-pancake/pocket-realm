# Pocket Realm — Inno Installer Payload Extraction (WoW-1.12.1_install.rar)

Written against `feature/universal-client-installer` @ `df8b579` (0.103.0-alpha staged, versionCode 8), 2026-08-27. Extends the universal client installer (M0–M5) so Blizzard-era **Inno Setup installer payloads** — currently rejected with VAL-12 — install in-app like every other client source.

## Mission

`WoW-1.12.1_install.rar` (RAR5, 4.97 GiB) contains an **Inno Setup 5.3.5** installer (`setup.exe` + `setup-1..4.bin`) whose payload is a complete vanilla 1.12.1 client rooted at `{app}\` — verified by extracting it with innoextract 1.9: `WoW.exe` is exactly 4,775,986 bytes / PE version **1.12.1.5875**, with all 14 `MPQ\x1a` archives, standard DLLs, realmlist.wtf, docs and cinematics. Make Pocket Realm **detect Inno installer payloads and install the client from them on device** — no Windows, no installer execution — through the existing hardened archive-import lane (staging, journal, resume, verify, atomic publish, data prep).

## Ground truth (all verified on the real files, not inferred)

- **Payload identity**: Inno Setup Setup Data **(5.3.5)**, ANSI (not Unicode), **not passworded**, LZMA1, app title "World Of Warcraft Classic" 1.12.1, publisher "PreBound" (a repack, not a Blizzard compile — `app_id {9FAD220A-…}`).
- **setup.exe (325,224 B)**: PE with the Inno offset table in a **PE resource named 11111** (RCDATA), magic `rDlPtS\xcd\xe6\xd7{\x0b*` (5.1.5+ layout: 12-byte magic, u32 revision, u32 ignored, u32 exe_offset, u32 exe_uncompressed_size, u32 exe_crc, u32 header_offset, u32 data_offset — CRC32 over everything after the magic). Real values: header_offset=0x10200, data_offset=0 (**external slices**). A pre-5.1.5 fallback exists ("Inno" magic at 0x30 + pointer with bitwise-not check).
- **Version signature**: 64 bytes at header_offset ("Inno Setup Setup Data (5.3.5)"); known-string table maps to version constants.
- **Block framing (header streams)**: `[u32 headerCRC][u32 storedSize][u8 compressedFlag]` — CRC32 over the 5 bytes (size+flag); compressedFlag 1→LZMA1 (≥4.1.6), 0→stored. The storedSize bytes are `[u32 crc32][≤4096 B]` frames wrapping the **compressed** bytes (decompressor reads through the framing — first 4 payload bytes ARE the first frame's CRC, verified). LZMA1 stream = props byte (0x5d) + LE32 dict (0x200000 = 2 MiB) + raw LZMA1 **without end marker** — decoded cleanly with python `FORMAT_RAW` consuming exactly the framed bytes (64,232 B header stream, zero errors). This ordering confusion cost an hour: boost::iostreams pushes filters stack-like (last pushed = nearest source), which is why innoextract's `block.cpp` reads the same way.
- **Header layout** (5.3.5, ANSI, from innoextract `setup/header.cpp` + `info.cpp`): length-prefixed strings (u32 + bytes, decoded via language codepage; this payload = cp1252), counts for languages/messages/permissions/types/components/tasks/directories/files/data entries/icons/ini/registry/delete/run, `windows_version_range`, colors, MD5 password hash + 8-byte salt (present even when unused — `header::Password` flag says whether it's real), `extra_disk_space_required`, `slices_per_disk`, enums, compression method (stored/zlib/bzip2/lzma1 for [4.2.6, 5.3.9)), architecture flags, more enums, then the big options bitfield (LSB-first, version-gated bit set). After the primary stream: wizard images + optional decompressor/decryptor DLLs (skip), then a **second block** with the **data entries**. Every entry type in between (messages…uninstall run) must be parsed field-exactly to skip — mechanical ports of the innoextract `load()` functions.
- **Language entries** carry an explicit u32 codepage (non-Unicode, ≥4.2.2); `info` uses language[0] (preferring 1252) for string decoding.
- **File entries** (5.3.5): encoded strings source/destination/install_font_name/strong_assembly_name, condition strings (components/tasks/languages/check/before/after), windows_version_range, **u32 location → index into data entries**, u32 attributes, u64 external_size, i16 permission, options bitfield, type enum (UserFile/UninstExe). Destinations are raw Inno constant strings — this payload uses `{app}\WoW.exe` etc. (innoexpand renders "app\…").
- **Data entries** (5.3.5): u32 first_slice, u32 last_slice (0-based), u32 chunk_offset, u64 file_offset (offset within the decompressed chunk stream — solid compression: several files share one chunk), u64 file_size, u64 chunk_size (total compressed bytes), **MD5 of the final file bytes** (5.3.5 ≥4.2.0 <5.3.9), FILETIME i64, file_version 2×u32, options bitfield (bits: VersionInfoValid, VersionInfoNotValid, TimeStampInUTC, IsUninstallerExe, **CallInstructionOptimized**, Touch, **ChunkEncrypted**, **ChunkCompressed**, SolidBreak; <4.2.5 implies ChunkCompressed). ChunkCompressed → chunk compression = header.compression; ChunkEncrypted → ARC4+MD5 salted (5.3.5) — **rejected** (encrypted).
- **Slices** (`setup-N.bin`): 8-byte magic `idska16\x1a`/`idska32\x1a` + u32 slice_size (logical size incl. 12-byte header; ≤ file size), data from offset 12; reads run off the end into the next slice transparently. Naming `<stem>-<n>.bin` (n from 1; slices_per_disk>1 uses `1a` style — not this payload). innoextract also accepts the header's `base_filename` as an alternate stem, case-insensitively.
- **Chunk streams**: seek (first_slice, chunk_offset) → 4-byte magic `zlb\x1a` → [8-byte salt + ARC4 if encrypted — not ours] → chunk_size bytes = one stored/zlib/**LZMA1** (props+dict+raw, same shape as blocks) stream decompressing to the concatenation of every file that references this chunk, at their file_offset/file_size. Files must be consumed in (slice, offset) order; `file.offset` is monotonic within a chunk.
- **x86 call filter** (files flagged CallInstructionOptimized — exes/dlls): inverse of Inno's `TransformCallInstructions`. For 5.2.0 ≤ v < 5.3.9: `inno_exe_decoder_5200(flip_high_bytes=false)` — E8/E9 opcodes not spanning 64 KiB blocks whose addr high byte ∈ {00,FF}: lower 3 bytes -= (offset_of_instruction_end & 0xFFFFFF). (<5.2.0 uses the 4108 variant; ≥5.3.9 flips the high byte when bit 23 is set.) Applied per file **after** decompression, before MD5.
- **Licensing** (the whole reason this is possible): innoextract 1.9 is **zlib**-licensed (verified from the shipped LICENSE.txt) — legal to use as the format reference for a GPL-3.0 Kotlin implementation, with credit. XZ for Java (`org.tukaani:xz`, already a dependency since Phase 0 for 7z) is **0BSD**. Inno Setup's own issrc (the primary spec for block framing and the call transform) is Inno's license but we read it as documentation, not code. No Blizzard bytes are committed — fixtures stay synthetic (repo rule).

## Design

1. **Detection.** `ArchiveQuickCheck` currently rejects `setup.exe + setup-*.bin` with VAL-12. New verdict **`InstallerPayload`**: same signature, routed to the Inno lane instead of rejection (installer payloads that are NOT Inno — e.g. InstallShield/MSI — keep VAL-12 with unchanged copy; ISOs keep VAL-11). The staged archive is **extracted to a scratch dir** `client/incoming/<importId>.pkg.d/` (ZIP/7z via existing random-access sources, RAR via libarchive streaming — same `recoverAndFinish` mechanics pointed at the scratch dir), then `InnoSetupReader` parses `setup.exe` in the scratch dir. Pre-copy gates from the parsed header: supported version (5.0.0–5.5.9 incl. Unicode), not encrypted (`header::Password`/`EncryptionUsed` → VAL-13 "password-protected installer"), ≥1 file under `{app}` containing WoW.exe + Data/ (locate on names — same `findClientRoot` after stripping `{app}`), size caps. Detection summary tells the user: original app title/version, "installer payload — Pocket Realm extracts the 1.12.1 client from it", file count/size, exclusions (non-{app} entries).
2. **`InnoSetupReader`** (pure Kotlin, JVM-testable — unlike the libarchive JNI): PE resource walk (rsrc dir → ID 11111 → RVA→file offset; MZ/PE parse identical in spirit to `ClientPeIdentity`), offset table + CRC, version table, block reader (framing + CRC + sub-chunk CRCs + LZMA1/zlib/stored), full 5.x header parser (entry types parsed field-exactly; those we don't model are parsed-and-dropped), language codepage selection (cp125x single-byte + UTF-16LE; DBCS → VAL-13), file/data-entry tables, slice file set with stem fallback + case-insensitive lookup, chunk stream reader with cross-slice reads, the 4108/5200/5200-flip call filters, per-file MD5. **LZMA1 without end marker**: `org.tukaani.xz.LZMAInputStream`'s raw constructor with `uncompSize=-1` expects a marker; if the real streams trip it (spike I0 decides), vendor the 0BSD `LZMAInputStream` into `importer/lzma/` with a stop-at-input-exhaustion patch and a NOTICE header — no license cost, no behavioral guesswork.
3. **`InnoArchiveSource : ImportSource`.** `inventory()` = `{app}`-rooted file entries in chunk-sequential order (entries outside `{app}` and UninstExe files are reported as excluded and never inventoried), rebased so WoW.exe lands at generation root — publish/data-prep see an ordinary client tree. `open(entry)` = open the owning chunk (LZMA1/zlib/stored), skip `file_offset` bytes, stream `file_size` bytes through the call filter when flagged; MD5 verified on the fly; `SOURCE_CHANGED` fingerprint = name+size+MD5. Solid-compression prefix skips are decompress-and-discard (a resumed import may re-pay the prefix of its chunk once — journaled per file as today).
4. **Pipeline wiring** (`ManagedClientImporter.runArchive`): stage → sniff → installer-payload branch → scratch extract → `InnoSetupReader` quick gates → `finishStaging` + DISCOVERING summary → `InnoArchiveSource` → existing preflight/copyAllEntries/verifyManagedCopy/publish flow untouched. Identity hard gate: post-copy `ArchiveClientScanner.verifyExtracted` (PE 1.12.1.5875 + MPQ headers) exactly like the RAR lane. Scratch dir deleted after publish and at terminal states alongside the staged `.pkg` (extend `StagedArchiveStore.reconcile`); cancellation retains it for resume.
5. **Planner**: the installer lane adds a scratch term ≈ archive size (peak = staged archive + scratch extract + extracted client ≈ 2× archive + client ≈ 14.7 GiB worst case for this payload) — same fail-closed arithmetic as the M1 staging term.
6. **UI/docs**: confirm-dialog branch ("Blizzard-era Inno installer — Pocket Realm will extract the client from it on device; needs ~2× the archive in free space"); progress card shows EXTRACTING per file as today; `FirstRunTutorial` wording gains "original installer archives (.zip/.7z/.rar containing setup.exe + setup-*.bin) are extracted for you — Windows installers you must run yourself are still refused"; Troubleshooting gains the new VAL-13 variants (password-protected installer, unsupported Inno version/DBCS codepage); `Game-Files-and-Import.md` two-lane contract updated; companion `install_client_windows.ps1` verdict for installer payloads becomes "installable by the Pocket Realm app" (7-Zip cannot read Inno; no PC extraction is added); THIRD_PARTY_NOTICES credits innoextract (format reference, zlib) and the vendored 0BSD LZMA code path if used.

## Non-goals

No installer execution (Wine or otherwise); no ARC4/encrypted installers; no Inno <5.0.0 or >5.5.9, DBCS codepages, LZMA2, bzip2-only headers, or `additional_locations` multi-part files (VAL-13 with actionable copy); no GOG Galaxy reassembly; no PC-side Inno extraction in the companion; no Blizzard asset bundling.

## Risk register

- **xz-java vs no-end-marker LZMA1** — spike I0 decides raw API vs 0BSD vendored decoder with a one-line stop condition. Low risk either way (license-free both paths).
- **Header parser field drift across 5.x** — mitigated by version gates ported from innoextract's battle-tested `version >=` chains + the I0 real-file parse + CRC checks at every layer (bad drift fails closed as VAL-13, never silently).
- **Solid-compression prefix cost on resume** — bounded (one chunk prefix re-decode per resume); the big MPQs are expected one-file-per-chunk (verify in I0).
- **On-device decode time** — LZMA1 of ~4.7 GiB is minutes, not hours (same class as the RAR lane); notification already shows per-file progress.
- **Scratch disk pressure** — planner term + scratch deleted before data prep; scratch GC mirrors the M2 staged-file reconciler.
